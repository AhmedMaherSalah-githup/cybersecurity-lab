# Web Application SOC Detection Rules

## 1. Purpose

This document defines detection logic for security events observed or simulated within the authorized OWASP Juice Shop laboratory.

The rules are designed to help a SOC analyst identify suspicious web application activity from HTTP and application logs.

These rules describe detection logic. They do not claim that a production SIEM was deployed during this assessment.

---

## 2. Detection Objectives

The detection strategy focuses on identifying:

1. Authentication abuse
2. Invalid JWT usage
3. Suspicious endpoint probing
4. Repeated server-side errors
5. Web application reconnaissance

The goal is to correlate individual HTTP events into patterns that may indicate malicious or suspicious activity.

---

## 3. Recommended Log Fields

A web application or reverse proxy should provide, where available:

| Field | Description |
|---|---|
| `timestamp` | Event date and time |
| `source_ip` | Client source address |
| `http_method` | HTTP method |
| `request_path` | Requested URI |
| `status_code` | HTTP response status |
| `user_agent` | Client user-agent |
| `username` | Authenticated identity, if available |
| `auth_result` | Authentication result |
| `response_time` | Server response duration |
| `request_id` | Correlation identifier |

These fields allow the SOC analyst to correlate authentication failures, endpoint probing, and application errors.

## 4. Detection Rule: Repeated Authentication Failures

### Rule ID

`WEB-AUTH-001`

### Objective

Detect repeated failed authentication attempts against web application authentication endpoints.

### Relevant Endpoint

```text
/rest/user/login

Detection Logic

Trigger an alert when the same source generates multiple HTTP 401 responses against authentication-related endpoints within a short time window.

Example logic:

source_ip
    |
    +-- multiple requests
    |
    +-- /rest/user/login
    |
    +-- HTTP 401
    |
    +-- short time window
    |
    v
Potential Authentication Abuse

Example Threshold

5 or more failed authentication attempts
from the same source IP
within 5 minutes

The threshold is an example detection baseline and should be tuned according to normal application behavior.

Analyst Questions

Is the source IP expected?

Is the activity associated with a legitimate user?

Are usernames being targeted sequentially?

Is the request rate abnormal?

Are multiple accounts being targeted?

Does the activity continue after successful authentication?

5. Detection Rule: Invalid JWT Signature

Rule ID

WEB-AUTH-002

Objective

Detect requests containing JWTs that fail signature validation.

Detection Indicator

Application logs containing an authentication error such as:

invalid signature

combined with:

HTTP 401

Detection Logic

HTTP request
     |
     v
Protected endpoint
     |
     v
JWT validation
     |
     +---- valid ----> HTTP 200
     |
     +---- invalid --> HTTP 401
                         |
                         v
                  invalid signature

SOC Interpretation

A single invalid JWT may result from:

Expired or malformed client state

Application/client synchronization problems

A user reusing an invalid token

Token manipulation

Automated probing


Repeated invalid signatures from the same source should receive additional investigation.

Analyst Questions

How many invalid JWT events occurred?

Did they originate from the same source?

Which protected endpoints were targeted?

Was there a successful login before the failures?

Did the source subsequently access the application successfully?

Is the source associated with a known user?

6. Detection Rule: Suspicious Endpoint Probing

Rule ID

WEB-RECON-001

Objective

Detect repeated requests to unexpected or nonexistent application endpoints.

Detection Indicators

Examples include:

HTTP 404
HTTP 500
Unexpected REST path
Repeated requests to different endpoints

A sequence such as:

/rest/test1
/rest/test2
/rest/admin
/rest/unknown

may indicate endpoint enumeration or application reconnaissance.

Detection Logic

Same source IP
      |
      +--> multiple unusual paths
      |
      +--> short time window
      |
      +--> repeated 4xx/5xx responses
      |
      v
Potential Web Reconnaissance

Analyst Questions

How many unique paths were requested?

Are the paths related to administrative functionality?

Did the source enumerate APIs systematically?

Did successful requests follow the failed requests?

Is the source a known scanner or monitoring system?

7. Detection Rule: Repeated Unexpected REST Errors

Rule ID

WEB-ERROR-001

Objective

Detect repeated server-side errors generated by unexpected REST requests.

Observed Lab Behavior

Unexpected /rest/* paths generated:

HTTP 500 Internal Server Error

The response also exposed detailed application error information.

Detection Logic

source_ip
    |
    +-- unexpected /rest/* request
    |
    +-- HTTP 500
    |
    +-- repeated occurrences
    |
    v
Potential Endpoint Probing

Security Relevance

Repeated 500 responses can indicate:

Endpoint enumeration

Automated reconnaissance

Malformed requests

Application abuse

Attempts to trigger unexpected application behavior


A single 500 response should not automatically be treated as malicious. Correlation and context are required.

9. False Positive Considerations

Detection rules should account for legitimate activity.

Possible false positives include:

Automated vulnerability scanners used by security teams

Browser extensions

Broken frontend requests

Monitoring systems

API clients

Expired sessions

Application testing

Development/debugging activity


Detection thresholds should therefore be tuned using normal application traffic before enforcing automated blocking.
## 10. Initial Analyst Response

When a detection is triggered, the SOC analyst should:

1. Validate the event and confirm that the source is not an approved scanner or monitoring system.
2. Identify the source IP and affected endpoint.
3. Review the surrounding HTTP requests and response codes.
4. Determine whether authentication was involved.
5. Check for a sequence of reconnaissance followed by authentication activity.
6. Correlate the event with available application, reverse-proxy, or host logs.
7. Preserve relevant evidence before modifying the environment.
8. Escalate the event when multiple indicators form a consistent suspicious pattern.

13. Detection Engineering Notes

The rules in this document are intentionally behavior-based.

A single HTTP status code should generally not be treated as proof of malicious activity.

Higher-confidence detections can be created by correlating:

Source IP
+
Request frequency
+
Unique endpoint count
+
HTTP status pattern
+
Authentication failures
+
JWT validation failures

This approach reduces false positives and provides better context for SOC analysts.
